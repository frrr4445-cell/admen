# Travel Touch — إصدار 1.3.0 | Vercel + Firebase Spark

هذه النسخة تنقل وظائف الخادم (ChatGPT وقراءة جواز السفر وPayPal) إلى Vercel Serverless Functions. يبقى Firebase مسؤولاً عن Authentication وFirestore وStorage، ولا تحتاج إلى Firebase Blaze لتشغيل هذه المسارات.

## ما الذي تغيّر؟
- `api/chat.js`: مساعد عربي يقرأ العروض المتاحة وحجوزات المستخدم وآخر رسائل المحادثة، ثم يحفظ الرسالتين في `chats/{uid}/messages`.
- `api/scan-passport.js`: OCR لصورة الجواز عبر OpenAI Vision، مع التحقق من تسجيل الدخول وحدود حجم الصورة.
- `api/create-order.js` و`api/capture-order.js`: إنشاء طلب PayPal والتحقق من التحصيل والمبلغ والعملة وإنشاء الحجز على Firestore من الخادم فقط.
- `api/paypal-webhook.js`: التحقق من توقيع PayPal Webhook لاستكمال الدفع عند إغلاق صفحة العودة.
- `api/admin-refund.js`: إصدار استرداد كامل من PayPal للمشرف فقط، بمفتاح idempotency وسجل تدقيق إداري.
- `api/chat-history.js`: استرجاع آخر 40 رسالة للمستخدم بعد التحقق من هويته.
- `api/admin-offer.js`: تعديل العرض من لوحة المشرف مع التحقق وتسجيل الحقول المعدلة في سجل التدقيق.
- `api/ticket-qr.js` و`api/checkin-ticket.js`: رموز QR موقعة للحجوزات المؤكدة والتحقق منها وتسجيل الوصول مرة واحدة للمشرف المخوّل.
- `checkin.html`: صفحة فحص QR بالكاميرا أو إدخال الرمز يدوياً.
- ضغط صور العروض في المتصفح إلى WebP بعرض أقصى 1200 بكسل قبل رفعها إلى Storage؛ حذف العرض يحاول حذف صورته المخزنة أيضاً.
- `api/delete-account.js`: حذف حساب الدخول والبيانات الشخصية بعد إعادة مصادقة حديثة، مع إخفاء هوية السجلات المالية المحتفظ بها ومنع الحذف أثناء وجود دفع/استرداد معلق.
- إضافة لوحة متابعة للمدفوعات التي تتطلب مراجعة أو استرداداً، وربطها بواجهة المشرف.
- إضافة اختبار محلي موحد عبر `npm test` للتحقق من صياغة ملفات JavaScript وHTML المضمنة وJSON وبعض ضوابط الأمان.
- `tt-backend.js`: إرسال Firebase ID token إلى مسارات Vercel بدلاً من Firebase Functions.
- `checkout.html`: استبدال OCR التجريبي بمسح فعلي للصورة مع تصغيرها في المتصفح.
- `index.html`: إضافة نافذة مساعد ذكي عائمة.
- `vercel.json`: السماح بالكاميرا من نفس الموقع فقط.
- أزيل مجلد Firebase Functions القديم حتى لا يبقى مسار نشر مدفوع غير مستخدم.

## إعداد Vercel (مطلوب قبل التشغيل)
من Vercel > Project > Settings > Environment Variables أضف:

1. `OPENAI_API_KEY`: مفتاح API من OpenAI. هذا المفتاح لا يوضع في ملفات الموقع.
2. `OPENAI_MODEL`: اختياري، الافتراضي `gpt-4o-mini`.
3. `OPENAI_VISION_MODEL`: اختياري، الافتراضي `gpt-4o-mini`.
4. `FIREBASE_SERVICE_ACCOUNT_JSON`: محتوى JSON كامل لحساب خدمة Firebase. أنشئ حساب خدمة مخصصاً بصلاحيات Firestore اللازمة فقط، واحفظ JSON في Vercel وليس GitHub.
5. `PAYPAL_CLIENT_ID`: REST App Client ID.
6. `PAYPAL_CLIENT_SECRET`: REST App Secret.
7. `PAYPAL_ENV`: ابدأ بـ `sandbox`، ولا تستخدم `live` إلا بعد الاختبارات.
8. `PAYPAL_WEBHOOK_ID`: معرّف Webhook بعد إنشائه في PayPal.
9. `TICKET_SIGNING_SECRET`: سر عشوائي لا يقل عن 32 حرفاً لتوقيع رموز QR؛ أنشئه مثلاً عبر `openssl rand -hex 32`.
10. `PUBLIC_APP_URL`: عنوان HTTPS الأساسي للموقع مثل `https://your-project.vercel.app` دون مسار إضافي.

بعد إضافة المتغيرات، أعد النشر Redeploy حتى تُقرأ في الدوال. الحزمة مثبتة على Node.js 24.x لتجنب إصدارات Runtime القديمة؛ تأكد من اختيار 24.x في إعدادات Vercel أيضاً إن كان إعداد المشروع يتجاوز قيمة `package.json`.

### إعداد Firebase Service Account
- من Firebase Console > Project settings > Service accounts أنشئ/استخدم حساب خدمة مخصصاً.
- خزّن ملف JSON كاملاً كقيمة `FIREBASE_SERVICE_ACCOUNT_JSON` في Vercel.
- لا تضع الملف داخل المشروع ولا ترفعه إلى GitHub.
- واجهات API تتحقق من Firebase ID token المرسل من المتصفح، ثم تستخدم Admin SDK لقراءة وكتابة Firestore. Admin SDK يتجاوز Firestore Rules؛ لذلك يجب حماية المفاتيح وعدم إضافة مسارات API غير محمية.

### إعداد PayPal Webhook
1. أنشئ REST API App في PayPal Developer Dashboard واختر Sandbox.
2. أضف Webhook URL: `https://YOUR-PROJECT.vercel.app/api/paypal-webhook`.
3. اشترك في الحدثين `PAYMENT.CAPTURE.COMPLETED` و`PAYMENT.CAPTURE.REFUNDED` حتى تتم مزامنة الحجز عند اكتمال التحصيل أو الاسترداد من PayPal.
4. انسخ Webhook ID إلى `PAYPAL_WEBHOOK_ID` في Vercel ثم أعد النشر.
5. اختبر دورة كاملة: الحجز المؤقت، إنشاء الطلب، موافقة المشتري، Capture، ظهور الحجز في `ticketWallet.html`، ثم اختبر فشل الدفع والإلغاء.
6. بعد نجاح Sandbox، أدخل بيانات Live وغيّر `PAYPAL_ENV=live` وأعد النشر.

## إعداد Firebase
- أبقِ Firebase Authentication وFirestore وStorage على خطة Spark.
- أضف نطاق Vercel إلى Authentication > Settings > Authorized domains.
- انشر القواعد والفهارس من جذر المشروع:
  `firebase deploy --only firestore:rules,firestore:indexes,storage`
- تأكد من تفعيل Email/Password في Authentication.
- أنشئ `admins/{uid}` يدوياً لحساب المشرف فقط.
- لم تعد بحاجة إلى `firebase deploy --only functions`.

## النشر
1. اجعل Vercel Root Directory هو المجلد الذي يحتوي `index.html` و`package.json` و`vercel.json`.
2. اربط مستودع GitHub أو ارفع المشروع عبر Vercel CLI.
3. أضف متغيرات البيئة المذكورة أعلاه.
4. انشر المشروع ثم نفّذ Redeploy بعد إضافة الأسرار.
5. تأكد من أن ملفات الموقع و`api/` في نفس جذر المشروع.

## تنبيهات مهمة
- استضافة Vercel Hobby قد تكون مجانية ضمن حدود الاستخدام والسياسات الحالية، لكنها ليست غير محدودة ولا تضمن بقاء الاستخدام التجاري مجانياً. راجع حدود حسابك في Vercel.
- استخدام OpenAI API منفصل عن اشتراك ChatGPT ويُحاسب حسب الاستخدام؛ لا يوجد ضمان أنه مجاني. ضع حدود إنفاق وتنبيهات في لوحة OpenAI.
- Firebase Spark لا يفرض ترقية Blaze على استخدام Firestore/Auth/Storage ضمن حدود Spark، لكن تجاوز الحصص قد يوقف الخدمة.
- OCR يتعامل مع بيانات جواز حساسة: الصورة تُرسل إلى OpenAI لاستخراج الاسم ولا تُحفظ في Firestore بواسطة هذا الكود. راجع سياسات الخصوصية والموافقة القانونية قبل الإنتاج.
- Webhook يحتاج Webhook ID صحيحاً وتوقيعاً صالحاً؛ لا تعلن الدفع مكتملاً إلا عند حالة `COMPLETED`.
- لم يتم الاتصال بحساباتك أو نشر المشروع أو إجراء معاملات Sandbox فعلية. الملفات معدّة برمجياً، لكن يلزم ضبط الأسرار ثم الاختبار الفعلي قبل استقبال أموال حقيقية.

## تحسينات الحماية في إصدار 1.1.0 (مستمرة في 1.2.0)
- نقل قفل العرض من مستند `offers` العام إلى `offerLocks` الخاص الذي لا يستطيع المتصفح قراءته أو تعديله. هذا يمنع كشف UID صاحب الحجز المؤقت ويعالج سباق فتح أكثر من نافذة دفع.
- مدة الحجز الأولية 3 دقائق. عند إنشاء طلب PayPal يمدد الخادم قفل الدفع إلى 30 دقيقة؛ هذا تمديد مقصود لإتمام صفحة PayPal وليس اختلافاً عشوائياً في المؤقت.
- حدود استخدام على مستوى عنوان IP والمستخدم لمسارات المساعد وOCR والحجز والتحرير والتأكيد، مع رفض Origin غير المسموح.
- مهلات زمنية لاتصالات OpenAI وPayPal، ورسائل أخطاء عامة لا تكشف تفاصيل الخادم.
- حفظ رسالتي المستخدم والمساعد في عملية Firestore Batch واحدة، مع سياق محدود وفلترة العروض المنتهية.
- تسجيل موافقة OCR في `consents` قبل إرسال الصورة، والتحقق من موافقة صريحة في الخادم، وتحديد حجم ونوع الصورة.
- التحقق من إجمالي المبلغ والضريبة والعملة قبل تأكيد الحجز، واستخدام قفل دفع ذريّ لمنع تعدد الطلبات لنفس العرض.
- تعارض المخزون بعد تحصيل PayPal يُعلّم `refund_required` للمراجعة اليدوية بدلاً من إصدار استرداد آلي فوري قد يسبب رسوماً أو خسارة عمولة.
- إضافة `/api/health` و`api/openapi.yaml` وصفحة `404.html` وتحديث Service Worker لمنع تخزين صفحات الحساب والدفع والـ API.
- إضافة رؤوس أمان HTTP أساسية وإيقاف التخزين المؤقت لواجهات API.

## إعدادات مطلوبة بعد النشر
1. أضف `PUBLIC_APP_URL` كرابط HTTPS الأساسي الصحيح للمشروع، وأضف نطاقات Preview المسموح بها إلى `ALLOWED_ORIGINS` عند الحاجة. لا تضع نطاقاً عاماً غير موثوق.
2. من جهاز موثوق بعد `gcloud auth login` فعّل سياسة TTL على حقل `expiresAt` للمجموعات `apiRateLimits` و`offerLocks` و`paypalWebhookEvents` بالأمر `npm run configure:ttl -- travel-touch-d71ac` (أو ضع معرّف مشروعك). يتطلب ذلك صلاحية إدارة Firestore في Google Cloud. راجع حالة السياسات في Firestore > Time-to-live؛ لا يُعد تشغيل السكربت إثباتاً أن Google أكملت التفعيل. من دون TTL ستظل المستندات القديمة موجودة وإن كانت غير فعالة.
3. قبل نشر النسخة الجديدة، شغّل ترحيل أقفال العروض القديمة مرة واحدة محلياً: عيّن `FIREBASE_SERVICE_ACCOUNT_JSON` في بيئة جهازك ثم نفّذ `npm run migrate:offer-locks`. هذا ينقل الأقفال الفعالة إلى `offerLocks` ويحذف حقول UID القديمة من مستندات العروض العامة. احتفظ بنسخة احتياطية أولاً. بعد ذلك انشر `firestore.rules` و`storage.rules` والفهارس. قفل العرض أصبح في مجموعة `offerLocks` ولا يجب السماح بقراءتها من العميل.
4. صفحة فحص التذاكر `checkin.html` تتطلب حساب مشرف مسجلاً، HTTPS، إذن الكاميرا، وإعداد `TICKET_SIGNING_SECRET`. QR لا يحتوي بيانات شخصية؛ بل رمز موقع محدود الصلاحية. حالياً صلاحية الفحص للمشرفين المسجلين في `admins` فقط؛ لم يُنشأ بعد نظام حسابات موظفي الفنادق/الشركاء.
5. راجع المدفوعات من لوحة المشرف. الحالات `refund_required` و`review_required` تظهر في لوحة المراجعة؛ زر «رد المبلغ بالكامل» ينفذ الاسترداد من PayPal بعد تأكيد المشرف. إذا أعاد PayPal حالة غير نهائية فستظل العملية `refund_pending` حتى إعادة التحقق. تُسجل العمليات في `auditLogs`، وهي للقراءة الإدارية فقط.
6. إعداد App Check الاختياري/الموصى به: سجّل تطبيق الويب في Firebase App Check واختر reCAPTCHA v3، ثم ضع Site Key العام في `firebase-config.js` داخل `appCheckSiteKey`. اختبر أولاً مع `ENFORCE_APP_CHECK=false`، وبعد التأكد من ظهور رموز App Check في طلبات API فعّل `ENFORCE_APP_CHECK=true` في Vercel وأعد النشر. لا تفعّل الإلزام قبل إضافة المفتاح وتسجيل نطاق الإنتاج.
7. فعّل تنبيهات الإنفاق في OpenAI، وحدود الاستخدام من لوحة OpenAI. حدود API في الكود تخفف الإساءة لكنها لا تضمن سقف تكلفة عالمياً.
8. اختبر دورة PayPal Sandbox كاملة قبل Live، بما فيها webhook والتكرار والرفض وانتهاء القفل.

## حذف الحساب والاحتفاظ المالي
- زر «حذف الحساب نهائياً» موجود في صفحة «حسابي». يتطلب تسجيل دخول حديثاً خلال آخر 5 دقائق؛ إذا انتهت المدة سجّل الخروج ثم الدخول مجدداً.
- تُحذف بيانات المستخدم والمحادثات وتذاكر الدعم والموافقات وطلبات SOS والتفضيلات وأقفال الحجز.
- تُحذف هوية المستخدم وبيانات المسافر من سجلات الحجوزات والمدفوعات، لكن تبقى السجلات المالية مجهّلة الهوية لأغراض المطابقة والمحاسبة. لا يُسمح بحذف الحساب أثناء وجود دفع أو استرداد معلق.
- إذا كان لديك التزام قانوني مختلف للاحتفاظ أو الحذف، راجع سياسة الخصوصية قبل تفعيل الوظيفة في الإنتاج.

## حدود النسخة بصراحة
هذه الحزمة توسّع المعالجة البرمجية وتضيف الاسترداد الإداري وحذف الحساب وسجل التدقيق ودعم App Check وQR موقّع لتسجيل الوصول وسجل المحادثات ورفع صور WebP، لكنها **لا تدّعي إغلاق البنود الـ120 كلها** لأن القائمة الأصلية المرقمة مع وصف كل عيب غير موجودة ضمن الملفات التي وصلتني. كما أن عزل شركاء B2B، التكاملات البريدية/WhatsApp، تصدير PDF/المحاسبة، النسخ الاحتياطي المجدول، سياسات التأشيرات، الصيانة وAnalytics تحتاج تعريف متطلبات ومزودات خارجية و/أو إعدادات حسابات. لا يمكن تنفيذها أو التحقق منها بمجرد تعديل ملفات الواجهة. راجع `AUDIT-120-STATUS-AR.md` قبل تشغيل معاملات حقيقية.


## تحسينات الأداء في الإصدار 1.2.1
- الصفحة الرئيسية تعرض آخر نسخة عامة من العروض من `sessionStorage` فوراً إذا كانت أحدث من 60 ثانية، ثم تحدّثها بصمت من `/api/public-offers`.
- مسار العروض العامة يقرأ الحقول اللازمة فقط من Firestore، ويعيد بحد أقصى 100 عرض متاح، مع CDN cache لمدة 30 ثانية و`stale-while-revalidate=60`.
- عند تعطل المسار العام، تعود الصفحة إلى `TT.watchOffers` كمسار احتياطي حتى لا تفقد القدرة على عرض العروض.
- صور بطاقات الصفحة الرئيسية تستخدم بالفعل `loading=lazy` و`decoding=async`.
- لا يوجد Cron لإبقاء الدوال دافئة: طلبات keep-alive لا تضمن منع cold starts، وقد تستهلك الحصة دون ضمان أداء. كما لا يُدّعى أن Edge يرد خلال 20ms أو أن PageSpeed سيصل إلى 99-100 دون قياس فعلي.
- لم يتم استبدال Firestore SDK بـ Lite أو تشغيل IndexedDB Persistence في هذا الإصدار؛ لأن `tt-backend.js` مشترك بين صفحات تسجيل الدخول والحجوزات واللوحة ويعتمد على listeners ومعاملات وعمليات كتابة. فصل SDK يتطلب تقسيم التطبيق إلى وحدات مستقلة واختبارات متصفح/مزامنة.
- لم نضف ضغط الصور في لوحة الشركاء لأن الإصدار الحالي لا يحتوي على مسار رفع صور عروض من لوحة الشركاء؛ الصور تُستهلك كرابط `image` محفوظ مع العرض. أضف ضغط WebP عند بناء مسار رفع فعلي.
- روابط PayPal للعودة والإلغاء تستخدم الآن المسارات النظيفة `/payment-success` و`/checkout` المتوافقة مع `cleanUrls`.
- قواعد Firestore تسمح بالاستعلامات العامة للعروض حتى 100 سجل، مع إبقاء استعلامات المشرف خاضعة لصلاحية المشرف.
- شغّل `npm test` بعد أي تعديل. اختبار الأداء الحقيقي يتطلب نشر نسخة اختبار وتشغيل Lighthouse/PageSpeed على الهاتف وسطح المكتب.


## وظائف تحتاج إعداداً خارج الملفات
- لوحة المشرف موجودة في `dashboard.html` وتشمل إنشاء العروض وعرضها وبيعها وحذفها وتعديل السعر/المزود/الغرفة، ومراجعة المدفوعات وتذاكر الدعم وسجل التدقيق. تتطلب مستند `admins/{uid}`.
- قواعد Storage تسمح برفع صور العروض للمشرف فقط، وصور المستخدم داخل مساره الشخصي فقط. صور العروض تُضغط WebP في المتصفح.
- لم تتم إضافة استرداد تلقائي يطلبه العميل: يلزم أولاً تعريف سياسة إلغاء واضحة (المواعيد، الرسوم، الاستثناءات) ثم تنفيذ موافقة/رفض وربطها بحالة PayPal. لا يجوز رد الأموال آلياً دون سياسة معتمدة.
- لم تتم إضافة عملات متعددة أو بوابة دفع محلية أو نظام شركاء متعدد المستأجرين. هذه تتطلب مزود دفع وحسابات تاجر واتفاقات تسوية، وتصميم صلاحيات وعزل بيانات قبل عرضها كميزة إنتاجية.
- لا يمكن تفعيل Live PayPal أو ربط نطاق Vercel أو App Check نيابة عن مالك الحساب دون الوصول إلى حساباته ومفاتيحه. ابدأ بـ Sandbox.

- عمليات الاسترداد تمر عبر `/api/admin-refund` وتستخدم مفتاح PayPal idempotency. لا تمنح أي مستخدم صلاحية مشرف إلا بعد التحقق من هويته.

### البريد التأكيدي (Resend)
- أنشئ حساب Resend، تحقق من نطاق الإرسال، ثم أضف `RESEND_API_KEY` و`TRANSACTIONAL_EMAIL_FROM` إلى Vercel Environment Variables.
- يرسل الخادم رسالة تأكيد بعد نجاح الدفع وإنشاء الحجز. لا تُرسل الرسالة من المتصفح ولا يحتوي المشروع على مفتاح البريد العام.
- تحفظ حالة الإرسال في سجل الدفع (`emailStatus`: `sending` أو `sent` أو `failed`). فشل البريد لا يلغي الحجز ولا يغير حالة الدفع.
- يجب أن يكون بريد العميل موجوداً في حساب Firebase Authentication. اختبر الإرسال أولاً إلى بريد تملكه في بيئة Sandbox.
- هذه الرسالة تحتوي ملخص الحجز ورقم الحجز، ولا تتضمن QR أو بيانات جواز السفر.

### الدفع السريع والرموز
- زر الدفع السريع على الهاتف يختصر بدء عملية الدفع، لكنه لا يتجاوز مراجعة البيانات أو موافقة PayPal النهائية.
- صفحة `ticketWallet.html` تنشئ QR من رمز قصير العمر وموقّع من الخادم، ولا تضع بيانات المسافر داخل QR. يلزم إعداد `TICKET_SIGNING_SECRET` وتسجيل دخول المشرف في صفحة `checkin.html`.

### فحوصات الإصدار
شغّل `npm test` قبل النشر. نجاح الاختبارات الثابتة لا يثبت اتصال Firebase/PayPal/Resend ولا يغني عن اختبار Sandbox واختبار الهاتف والمتصفح.

### ملاحظات الترحيل

الواجهات الحالية تستخدم Firebase Web SDK عبر ES Modules من CDN، بينما وظائف Vercel الحالية CommonJS/JavaScript وتعتمد على `api/_lib/common.js`. لم تُعد تسمية مسارات API إلى `.ts` في هذه المرحلة حتى لا تنكسر إعدادات Vercel أو روابط العملاء. الخطوة التالية الآمنة هي ترحيل كل endpoint على حدة إلى TypeScript مع اختبارات تكامل فعلية وبيئة staging، ثم تحديث `vercel.json` وOpenAPI بالتزامن.
